# YEW — release recipe

_Plan §7 W5, §3.5, §6.4, §8 Q4. What is done in this repository and what stays `[owner]` (a
device, a store account, a public server, a signing identity). The threat review is
`docs/security-review.md`, the license listing `docs/licenses.md`._

## 1. Reproducible build

**Toolchain, pinned where.**

| Tool | Version | Pinned in |
|---|---|---|
| Rust | 1.92.0 stable (`rustfmt`, `clippy`) | `rust-toolchain.toml` |
| Flutter / Dart | 3.47.5 stable / 3.13.4 | `app/pubspec.yaml` (`environment`), CI reads the README table |
| `flutter_rust_bridge` crate, codegen, Dart package | 2.13.0, all three | `core/Cargo.toml` (`=`), `app/pubspec.yaml`, `scripts/gen-bridge.sh` (refuses another codegen) |
| Android NDK | 28.2.13676358 | `app/android/app/build.gradle.kts` |
| protoc | any 3.x (36.1 used) | `core/build.rs`; the `.proto` files are pinned, not the compiler |
| `cargo-ndk` | latest | `scripts/build-core-android.sh` |
| Xcode | the owner's; minimum iOS 15.0 | `IPHONEOS_DEPLOYMENT_TARGET` |

**Rust.** Every direct dependency is `=x.y.z` (`core/Cargo.toml`); `Cargo.lock` is committed;
CI and the release builds use `--locked`, so a lock drift fails instead of resolving. The
release profile is `lto = true, codegen-units = 1, strip = true` (`Cargo.toml`). Cargo builds
are reproducible for the same toolchain, lock, target and profile up to the absolute source
path embedded in panic strings (`strip` removes symbols; pass
`--config 'build.rustflags=["--remap-path-prefix", "<workspace>=/yew"]'` for a path-independent
binary — a `[owner]` CI setting once the release machine is known).

```bash
# core for the host (tests, yew-cli)
cargo build --release --locked --workspace
cargo test --workspace --locked
# core for the phones
scripts/build-core-ios.sh        # aarch64-apple-ios + -sim → app/ios/Frameworks/YewCore.xcframework
scripts/build-core-android.sh    # aarch64/x86_64 linux-android → app/android/app/src/main/jniLibs
# the app
(cd app && flutter pub get && flutter build appbundle --release)   # [owner] with the signing config
(cd app && flutter build ipa --release)                            # [owner] with the Xcode identity
```

**The generated code is verified, not trusted.** `core/src/frb_generated.rs` and
`app/lib/src/rust/` are committed. CI (`.github/workflows/ci.yml`, job `core-macos`) installs
`flutter_rust_bridge_codegen` at the version read from `core/Cargo.toml`, runs
`scripts/gen-bridge.sh` and fails on `git diff --exit-code` over both outputs: a bridge edited
by hand, or generated by another version, cannot merge. The same job builds the iOS core
(unsigned) so a broken cross-compile is caught without a device.

**The protocol is pinned.** `proto/*.proto` must be byte-identical to
`lightwalletd-dd/walletrpc/` at the commit in `proto/PIN`; `scripts/check-proto-pin.sh` diffs
them when the sibling checkout exists (the workspace) and prints the pin otherwise (CI). A
re-copy of the protos is a commit that updates `proto/PIN`.

**Other gates in CI.** `cargo fmt --check`, `clippy -D warnings`, `cargo test --locked`,
`scripts/check-deps.sh` (direct dependencies ⊆ `scripts/allowed-deps.txt`),
`scripts/check-licenses.sh` (§3), `scripts/audit.sh` (§2), `flutter analyze`, `flutter test`,
`scripts/check-app-imports.sh` (no crypto / network / database import under `app/lib`),
`scripts/check-trust-text.sh` (the trust statement in the app equals `docs/trust.md`).

## 2. Dependency audit

`scripts/audit.sh` runs `cargo audit --json` over `Cargo.lock` against the RustSec database.
It **blocks** on an advisory that has a patched version (the fix is a `Cargo.toml` bump, which
is an allow-list-neutral change when it stays within the same crate) and **prints without
failing** advisories with no fix yet and warnings (unmaintained, unsound, yanked), which are
recorded by hand in `docs/security-review.md`. First run (2026-09-25, 227 crates, database of
1,269 advisories): **0 vulnerabilities, 0 warnings**.

Upgrading a dependency to clear an advisory never changes `scripts/allowed-deps.txt` unless the
fix moves to another crate; that case is a recorded decision in the plan (§3.3), not a CI
edit.

## 3. Licenses

`docs/licenses.md` is the listing; `scripts/check-licenses.sh` regenerates it (`--print`) and,
without a flag, fails CI when a crate's SPDX expression has no identifier in the allowed
permissive set. The store builds must ship the Apache 2.0 text with the app (`ring` and other
Apache-2.0 crates): `[owner]`, §7.

## 4. Default endpoints

The list lives in the core: `net/tls.rs` `default_servers(network)` (bridged as
`default_servers`), read by Onboarding to prefill the server field.

| Network | Entries | Why |
|---|---|---|
| mainnet | **none** | plan §8 Q4: the owner supplies the public `lightwalletd-dd` endpoints (host, port, certificate) once they exist; nothing ships that trusts a server nobody vetted. Onboarding asks for one. |
| testnet | none | the same, until the testnet run (§8) has a host |
| regtest | `127.0.0.1:9067` plain | the local devnet (the Android emulator reaches it as `10.0.2.2:9267`, typed) |

To ship an endpoint: add a `DefaultServer { address: "lwd.example:443", plain: false }` to the
mainnet arm, and optionally its certificate for pinning (§5). The user can always type another
server; a server is probed (`GetLightdInfo` chain name, `taddrSupport`, `GetYellowbackInfo`
`rpcversion`) before it is saved.

## 5. Certificate pinning

`Server::ca_pem` (core) pins a PEM certificate — the server's own self-signed certificate or the
private CA that issued it — as the **only** trust anchor; the system roots are not consulted
when it is set. `yew-cli --ca-pem PATH`. A SHA-256 fingerprint pin needs `rustls` as a direct
dependency (an allow-list decision) and is not implemented; `docs/security-review.md` S-3b.
The app has no pinning field yet: it needs one bridge parameter on `probe_server`,
`create_wallet`, `unlock`, `set_server` and a Settings field — deferred, listed in the README's
owner list. When the mainnet endpoint is a Let's Encrypt host, pinning is unnecessary (system
roots); when it is a self-signed `lightwalletd-dd`, pinning is how the app trusts it.

## 6. Crash reporting and telemetry: none

There is no crash reporter, no analytics, no update check. The app's Dart packages
(`flutter_rust_bridge`, `flutter_secure_storage`, `local_auth`, `path_provider`, `qr_flutter`,
`mobile_scanner`, `cupertino_icons`) open no socket; `scripts/check-app-imports.sh` refuses any
HTTP or socket import under `app/lib`; the only network user is the core's gRPC client, to the
one server in Settings, and the `INTERNET` permission exists for it alone. The core's bridge
init installs a panic backtrace hook only, not the bridge's default console logger (W5 review
A-2). A future crash reporter would be **off by default** and a recorded decision.

## 8. Signing `[owner]`

- **iOS**: an Apple Developer team; in Xcode set the Runner target's team and bundle id, add
  `YewCore.xcframework` (`scripts/build-core-ios.sh`) to the target with `-force_load` (or the
  frb dummy-method pattern) so the linker keeps the bridge symbols; `flutter build ipa
  --release`; upload with Transporter / `xcrun altool`. TestFlight first.
- **Android**: a release keystore (`keytool -genkey -v -keystore yew-release.jks -keyalg RSA
  -keysize 4096 -validity 10000 -alias yew`), `app/android/key.properties` (untracked) and the
  `signingConfigs.release` block in `build.gradle.kts` (the Flutter template comment shows
  where); `flutter build appbundle --release`; Play Console internal testing track first. Enrol
  in Play App Signing so the upload key can be rotated.
- Never in CI (`ci.yml` states it); the signing material never enters this repository.

## 9. The testnet plan `[owner]` (plan §7 W5, third item)

The ≥ 4-week run needs, in order:

1. **v3 A7** (`docs/plans/yellowback-v3-development-plan.md`): the testnet activation of the
   Yellowback soft fork with attestors running — YEW's mint / redeem / claim paths need an
   *armed* network (a price bundle per block); before A7 the app can do YEC and YED transfers
   only where an index exists.
2. **A public `lightwalletd-dd`** built from `feature/yellowback-price-attest` at or after
   `proto/PIN`, started with `--yellowback` against a testnet `ycashd` (the fork) that runs
   with `-yellowback` and **`-insightexplorer`** (the address index `GetAddressUtxos` /
   `GetTaddressTxids` / `GetAddressTokens` need). TLS: a public host name with a Let's Encrypt
   certificate (system roots, no pinning) or a self-signed certificate published with the
   endpoint (pin it, §5). Ports: lightwalletd's 9067 or 443 behind a TLS terminator that
   speaks HTTP/2 end to end (gRPC needs `h2`, not HTTP/1.1 upgrade). Record the host in
   `default_servers(Testnet)` (§4) so the testers do not type it.
3. **Two phones** (one iOS, one Android) with the signed test builds (§8), the M1 and M2
   integration tests run once by hand against the public endpoint
   (`app/integration_test/m1_flow_test.dart`, `m2_flow_test.dart`), then the 4 weeks of
   ordinary use: receive, send YEC, send YED, mint at the three term classes, let one mint
   lapse and sweep it, redeem at lock height, claim after a price shock (the attestors'
   `--shock` on testnet), restore from seed on the other phone, import the exported key into
   a testnet YecWallet.
4. **What to record**: every gate refusal with its verdict, every sync error, the battery and
   data use of the 15-second mint poll, the time to first sync from a birthday. Anything the
   core refuses that the node accepts, or the reverse, is a bug against the client contract
   (lightwalletd plan §5) and gets a row in the plan.

Exit criterion: four weeks without a lost transaction, a wrong balance or a stranded carrier;
then the mainnet endpoint list (§4) and the store submissions (§7).
